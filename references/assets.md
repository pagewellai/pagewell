# Images and files

A document can reference images, PDFs and other files. They live beside the
document, not inside it.

## In a document

Write a **relative path**, exactly as if the file sat next to your Markdown:

```markdown
![Architecture](img/arch.png)

[The full report (PDF)](files/q3-report.pdf)
```

Then put the file there and publish the document — the files it references go
up with it, into the same Documents page:

```
post/
  intro.md            ← writes ![…](img/arch.png)
  img/arch.png        ← the file
  files/q3-report.pdf
```

```
pagewell publish post/intro.md --json     # "assets": 2; anything it could not take is in missing_assets
```

The path in the document is resolved **relative to the document**, so
`img/arch.png` from `guide/intro.md` means `guide/img/arch.png`. That is the
only rule; there is nothing else to learn. `publish` reads only files inside the
document's folder — not hidden ones, not through symlinks, only the types below —
and lists each reference it skipped with the reason in `missing_assets`. Read
those out: on the page they are broken images.

A folder kept in sync with a Space the user named does the same through
`pagewell push --assets --json`. An anonymous `publish --anonymous` is one file
and refuses a document with local files.

Absolute URLs (`https://…`) are left alone. PageWell never fetches them for you
— if you want the image to survive, upload it.

## What the push reports

```
create       1
update       0
unchanged    0
delete       0
files        3
to upload    4 blobs · 1.2 MB
```

`files` is counted separately from `create` on purpose: "1 new page and 12
images" is two different facts, and folding them together would make you report
"13 new pages".

Bytes are content-addressed, so pushing the same image twice, or the same image
from two documents, costs nothing the second time.

## What you can upload

| | |
|---|---|
| Images | `.png` `.jpg` `.jpeg` `.gif` `.webp` `.avif` `.svg` |
| Documents and data | `.pdf` `.csv` `.json` `.txt` `.zip` |
| Fonts | `.woff2` `.woff` |
| Size | **25 MiB each** (a document is 5 MiB) |

Anything else is refused, and the message lists what is accepted. The type a
reader's browser is told is decided **by the server from the extension** — not
by anything the uploader sends.

Video is not on that list yet. A short clip usually belongs on a video host,
linked; the point of this list is files the document itself needs.

## When the file is missing

`pagewell check` and `pagewell preview --once --json` both report it:

```json
{"doc": "guide/intro.md", "kind": "asset",
 "message": "img/arch.png is referenced but there is no file at guide/img/arch.png"}
```

The image stays broken rather than disappearing — that is deliberate. A broken
image says "something belongs here"; a silently removed one says nothing.

## Inline base64 images

An HTML page generated by an AI usually carries its images as
`data:image/png;base64,…`. Three things follow, and all three are real:

- the same picture is stored again in every document that uses it;
- base64 is 33% larger than the bytes, and it counts against the document's
  5 MiB;
- the reader's browser cannot cache it, so fixing one typo re-downloads
  every image.

`pagewell publish` pulls anything over 1 KiB out into a file of its own by
default. Small icons stay inline, where inline is the right answer.

⚠️ A single inline image over roughly 190 KiB is **dropped entirely** by the
sanitiser — the page opens, the picture is simply not there. `check` warns
about this before you publish. Pull it out, or save it as a file.

## Publishing one file you already have

When you have a finished HTML document — a Claude artifact, a generated report,
a page you wrote by hand — there is no directory to sync and no config to write:

```
pagewell publish report.html --json
cat report.html | pagewell publish - --title "Q3 review" --json
```

One call: unless `--space` is explicit, it uses the account's internal Documents
container, which is not a user-visible Space; uploads the file and the local
files it references; pulls the inline images out; makes the page public
(searchable unless the owner turned indexing off, or `--no-index` was passed);
prints its stable URL. Targeting a Space requires Pro, and happens only when the
user named the Space.

```json
{"url": "https://p.pagewell.ai/s/AbCdEfGhIjKlMnOpQrStUvWxYzAbCdEf",
 "visibility": "public", "searchable": true,
 "render_mode": "sandbox",
 "reason": "含 <script>，将在隔离沙箱中运行；搜索引擎只能读到摘要",
 "assets_extracted": 4}
```

`url` is the page's own stable address —
`https://p.pagewell.ai/s/<32 letters>`, no share — and `visibility` is
`"public"`. The same setting can be applied later with
`pagewell visibility <node-id> public --json`.

**Read `render_mode` out loud.** An HTML page with a `<script>` in it runs in an
isolated frame, which means search engines see the summary and not the body.
That is the right trade for an interactive page and the wrong one for an
article. If they wanted an article, write Markdown — it is always indexed.

`--visibility` defaults to `public`: permanent until changed, listed and
searchable, with no expiry, code, password or per-link permissions. `--no-index`
keeps such a page out of search engines and Explore while it stays readable by
link. Use
`unlisted`, `code` or `password` only for an explicitly restricted share.
`--no-share` uploads privately without creating a link.

## Uploading without a document

In the console there is a **Files** panel on each space: drop images in, and
each one offers the exact line to paste. Through the API it is one request:

```
POST /api/v1/spaces/{id}/assets?name=arch.png     (the raw bytes as the body)
```

It answers with the file plus a ready-to-paste `markdown` field. Files uploaded
this way sit at the top of the space, so a document at any depth references
them by the path that reaches them.

## They take room, and you can see exactly how much

Every uploaded byte counts against the owner's quota, the same as a document.
Content addressing means **the same file counts once**, however many documents
use it and however many times it is pushed.

```
pagewell usage --json                # totals, broken down
pagewell usage --files 10            # the ten largest, and which are unused
```

```
  28.3 KiB of 128.0 MiB (0%)
        documents  14.5 KiB · 120
            files  513.9 KiB · 17
            trash  0 B
  pending cleanup  0 B

  Largest files
  assets/06f06aeb7a62b4e0.png  469.3 KiB · Q3 review
           arch.png  (unused)  192 B · Client handbook
```

Two of those rows are the ones people miss:

- **`pending cleanup`** is space you already freed. Deleting a file removes the
  entry immediately; the bytes go at the nightly collection. When someone says
  "I deleted things and my usage didn't move", this is the answer.
- **`(unused)`** means no document references that file any more. It is the only
  column that tells you what is safe to delete — "18 MB" alone does not.

When a user is out of room, say the order: empty the trash, then the unused
files above, then upgrade. `pagewell usage` adds the file list automatically
once they are over.

## Deleting

Deleting a file removes the **entry**, not the bytes. Anything else pointing at
the same content keeps working, and the bytes are collected later, after a
cooling-off period. Documents that referenced the deleted entry show a broken
image — which is the honest outcome, and the reason the console says so before
you confirm.
